# Preview-Frontend Mismatch Bugfix Design

## Overview

The Visual Preview Mode in the FAQ Accordion block editor renders FAQ items using plain `<div>` elements that don't match the CSS selectors in `style.css`. The frontend uses native `<details>/<summary>` elements which get properly styled by `style.css` (borders, backgrounds, spacing, icon positioning, open-state indicators). The fix changes `renderVisualPreview()` in `edit.js` to use `<details>/<summary>` elements so the shared `style.css` (loaded in the editor via the `style` field in `block.json`) applies naturally without duplicating CSS rules.

## Glossary

- **Bug_Condition (C)**: The block is rendered in Visual Preview Mode (`layoutMode === "preview"`) within the editor context, causing HTML structure mismatch with `style.css` selectors
- **Property (P)**: The visual preview should use the same HTML element structure as the frontend (`<details>/<summary>`) so `style.css` rules apply identically
- **Preservation**: Classic edit mode rendering, frontend rendering via `render.php`, toggle interactions, custom inline styles, and `openFirstItem` behavior must remain unchanged
- **renderVisualPreview()**: The function in `blocks/faq-accordion/src/edit.js` that produces the accordion preview markup in the editor
- **render.php**: The server-side render callback that produces frontend `<details>/<summary>` HTML
- **style.css**: Shared stylesheet targeting `<details>/<summary>` selectors, compiled to `build/style-index.css` and loaded in both editor and frontend
- **getBlockClasses()**: Utility that computes wrapper classes (`has-icon-left`, `has-icon-right`, `has-no-icon`, `has-animation`) from block attributes

## Bug Details

### Bug Condition

The bug manifests when the block is in Visual Preview Mode in the editor. The `renderVisualPreview()` function renders `<div>` elements with classes (`faq-accordion-item`, `faq-accordion-summary`, `faq-accordion-content`) that don't match the CSS selectors in `style.css`, which target `details.faq-accordion-item`, `summary`, and content nested within `<details>`.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type BlockRenderContext { layoutMode: string, context: string }
  OUTPUT: boolean
  
  RETURN input.layoutMode = "preview"
         AND input.context = "editor"
         AND renderVisualPreview() uses <div> elements
         AND style.css selectors target <details>/<summary> elements
         AND visual styles are NOT applied to preview output
END FUNCTION
```

### Examples

- **Border missing**: Preview renders `<div class="faq-accordion-item">` but `style.css` targets `.faq-accordion-item` expecting a `<details>` element for the `[open]` attribute selector — border (1px solid #ddd) and border-radius (4px) still apply via class, but `[open]` accent border does not
- **Header unstyled**: Preview renders `<div class="faq-accordion-summary">` but `style.css` targets `.faq-accordion-item summary` (the element type) — background-color (#f9f9f9), padding, font-weight (600), and flex layout are missing
- **Open-state broken**: Preview uses `is-open` class but `style.css` uses `[open]` attribute selector — accent border color and icon rotation don't activate on open items
- **Icon positioning fails**: `style.css` rule `.has-icon-right .faq-accordion-item summary` targets the `<summary>` element — `flex-direction: row-reverse` never applies to the `<div class="faq-accordion-summary">`
- **Content separator missing**: `style.css` applies `border-top` to `.faq-accordion-content` inside `<details>` — the `<div>` structure in preview doesn't trigger this rule

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Classic Edit Mode (`layoutMode === "edit"`) must continue to render `FaqItemEditor` input fields with text inputs and action buttons
- Frontend rendering via `render.php` must continue to produce identical `<details>/<summary>` HTML
- Clicking/keyboard interaction on preview items must continue to toggle open/closed state via the `_open` attribute
- Custom inline styles (titleColor, titleFontSize, contentColor, contentPadding, etc.) must continue to apply in the preview
- `openFirstItem` must continue to show the first item expanded in both preview and frontend
- Block wrapper classes (`has-icon-left`, `has-icon-right`, `has-no-icon`, `has-animation`) must continue to be generated by `getBlockClasses()`

**Scope:**
All inputs where `layoutMode !== "preview"` should be completely unaffected by this fix. This includes:
- Classic editor mode rendering (input fields, action buttons)
- Frontend PHP rendering (render.php)
- InspectorControls panel behavior
- Block attribute changes and setAttributes calls

## Hypothesized Root Cause

Based on the bug description, the root cause is straightforward:

1. **Wrong HTML elements in renderVisualPreview()**: The function uses `<div className="faq-accordion-item">` instead of `<details className="faq-accordion-item">`, `<div className="faq-accordion-summary">` instead of `<summary>`, and relies on JavaScript-driven class toggling (`is-open`) instead of the native `[open]` attribute

2. **CSS selector mismatch**: `style.css` was written for the frontend's `<details>/<summary>` structure. Key selectors like `.faq-accordion-item summary` (element selector), `.faq-accordion-item[open]` (attribute selector), and the `details > summary` relationship all fail when `<div>` elements are used

3. **No redundant editor CSS**: The `editor.scss` file only styles the classic edit mode (input fields, action buttons). There are no fallback styles for the preview's `<div>` structure because the intent was always to share `style.css` — but the HTML was never aligned

4. **Open-state mechanism mismatch**: The preview uses a React state (`_open` → `is-open` class) but `style.css` uses the native `[open]` attribute on `<details>`. React can control the `open` attribute on `<details>` elements, making these compatible

## Correctness Properties

Property 1: Bug Condition - Visual Preview uses correct HTML structure

_For any_ block render in Visual Preview Mode (`layoutMode === "preview"` in the editor), the fixed `renderVisualPreview()` function SHALL produce `<details>` elements with class `faq-accordion-item` and `<summary>` elements for headers, matching the HTML structure that `style.css` selectors target, so that borders, backgrounds, icon positioning, open-state accents, and content separators render identically to the frontend.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

Property 2: Preservation - Non-preview rendering unchanged

_For any_ block render where the bug condition does NOT hold (`layoutMode !== "preview"` or context is frontend), the fixed code SHALL produce exactly the same output as the original code, preserving classic edit mode input fields, frontend `render.php` output, toggle interactions, inline styles, and `openFirstItem` behavior.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

**File**: `blocks/faq-accordion/src/edit.js`

**Function**: `renderVisualPreview()`

**Specific Changes**:

1. **Replace `<div>` wrapper with semantic match**: Change the inner wrapping `<div className="wp-block-wpbits-faq-accordion">` — actually this is unnecessary since `blockProps` already provides the wrapper. Remove this extra wrapper since the parent `<div {...blockProps}>` already has class `wp-block-wpbits-faq-accordion` via `useBlockProps`.

2. **Replace item `<div>` with `<details>`**: Change `<div className="faq-accordion-item ...">` to `<details className="faq-accordion-item" open={isOpen}>`. Use the native `open` attribute controlled by React instead of the `is-open` class. This allows `style.css` `[open]` selectors to apply.

3. **Replace header `<div>` with `<summary>`**: Change `<div className="faq-accordion-summary" ...>` to `<summary ...>`. Remove the custom `role="button"` and `tabIndex` since `<summary>` is natively interactive. Move `onClick` to toggle `_open` state (preventing native toggle to keep React in control).

4. **Keep `<div className="faq-accordion-content">`**: This element is correct as-is — `style.css` targets it by class within `<details>`. Add the inner `<div className="faq-accordion-content__inner">` wrapper for animation compatibility.

5. **Remove inline icon styles**: Remove the inline `style` object on `.faq-accordion-icon` that sets `marginRight`, `order`, `transition`, and `transform`. These are now handled by `style.css` rules (`.has-icon-right summary` for ordering, `[open] > summary .faq-accordion-icon` for rotation).

6. **Handle open/close with native details control**: Use `onToggle` event or override native toggle via `onClick` on `<summary>` with `e.preventDefault()` to keep React state in sync. This ensures the `_open` attribute and the native `open` prop stay synchronized.

7. **Always render content (for animation support)**: In the current code, content is conditionally rendered (`{isOpen && ...}`). Change to always render the `<div className="faq-accordion-content">` (matching frontend behavior where `<details>` handles visibility). For non-animated mode, CSS handles show/hide via the native details behavior.

**File**: `blocks/faq-accordion/src/editor.scss` (optional)

**Specific Changes**:
- Add minor editor-specific overrides if needed for `<details>/<summary>` elements in the editor context (e.g., preventing native toggle animation glitches, ensuring cursor pointer on summary).

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed code, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm that the CSS selectors in `style.css` do not apply to the current `<div>`-based preview structure.

**Test Plan**: Write tests that render the `Edit` component in preview mode and assert that the output HTML structure matches the selectors in `style.css`. Run these tests on the UNFIXED code to observe failures.

**Test Cases**:
1. **Element type test**: Assert `renderVisualPreview()` output contains `<details>` elements (will fail on unfixed code — produces `<div>`)
2. **Summary element test**: Assert output contains `<summary>` elements for headers (will fail on unfixed code — produces `<div class="faq-accordion-summary">`)
3. **Open attribute test**: Assert open items have native `open` attribute on `<details>` (will fail on unfixed code — uses `is-open` class)
4. **Content inner wrapper test**: Assert content has `.faq-accordion-content__inner` wrapper (will fail on unfixed code — missing inner wrapper)

**Expected Counterexamples**:
- Output HTML contains `<div class="faq-accordion-item">` instead of `<details class="faq-accordion-item">`
- Output HTML contains `<div class="faq-accordion-summary">` instead of `<summary>`
- Open items use class `is-open` instead of attribute `open`
- Possible cause: `renderVisualPreview()` was written with generic divs without considering CSS selector compatibility

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds (preview mode), the fixed function produces HTML structure matching `style.css` selectors.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := renderVisualPreview_fixed(input)
  ASSERT result contains <details class="faq-accordion-item">
  ASSERT result contains <summary> elements for headers
  ASSERT open items have <details open> attribute
  ASSERT icon is inside <summary> with class "faq-accordion-icon"
  ASSERT content has class "faq-accordion-content" inside <details>
  ASSERT content has inner wrapper "faq-accordion-content__inner"
END FOR
```

### Preservation Checking

**Goal**: Verify that for all inputs where the bug condition does NOT hold, the fixed function produces the same result as the original function.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT renderClassicEditor_original(input) = renderClassicEditor_fixed(input)
  ASSERT render_php_output is unchanged
  ASSERT toggleItem interaction still toggles _open attribute
  ASSERT inline styles still applied when custom attributes set
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many combinations of block attributes (titleColor, contentFontSize, iconPosition, etc.) automatically
- It catches edge cases where specific attribute combinations might break
- It provides strong guarantees that classic edit mode behavior is unchanged for all attribute states

**Test Plan**: Observe behavior on UNFIXED code first for classic edit mode and attribute application, then write property-based tests capturing that behavior.

**Test Cases**:
1. **Classic mode preservation**: Verify `layoutMode = "edit"` continues to render FaqItemEditor components with input fields
2. **Inline style preservation**: Verify custom titleColor, titleFontSize, contentColor, contentPadding all apply as inline styles in preview
3. **Toggle preservation**: Verify clicking summary toggles `_open` state on the item
4. **openFirstItem preservation**: Verify first item renders open when `openFirstItem === true`

### Unit Tests

- Test that `renderVisualPreview()` outputs `<details>` elements with correct classes
- Test that `<summary>` elements contain the icon and title tag
- Test that open state is controlled via the `open` attribute
- Test that `getBlockClasses()` output hasn't changed
- Test that classic edit mode render is unaffected

### Property-Based Tests

- Generate random FAQ item arrays (varying lengths, content) and verify preview always produces `<details>/<summary>` structure
- Generate random attribute combinations (iconPosition, enableAnimation, selectedIcon, openFirstItem) and verify correct CSS classes and attributes
- Generate random attribute states and verify classic edit mode output is unchanged

### Integration Tests

- Test full editor render with `layoutMode = "preview"` and verify styles apply visually (snapshot or computed style checks)
- Test switching between `layoutMode = "edit"` and `layoutMode = "preview"` and back
- Test that `style.css` selectors match the preview HTML by querying computed styles in JSDOM/testing-library
